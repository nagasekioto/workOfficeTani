# インシデント対応手順書

家政婦紹介事務所 人物管理システム（以下「本システム」）が乗っ取られた・情報が漏れた疑いがある、
と分かったときに何をするかをまとめた手順書です。

本システムは、求職者・求人者の**氏名・住所・電話番号・生年月日・家族構成・勤務先**を保有しています。
これらが外部に出た場合、個人情報保護法上の報告義務が発生する可能性があります（→ 第7章）。

---

## 0. この手順書そのものの保管ルール【最重要・最初に読むこと】

**この手順書は、守るべきシステムと同じ場所（リポジトリ内）にあります。**

つまり、リポジトリごと侵害された場合・PCが起動しなくなった場合・ランサムウェアで暗号化された場合、
**この手順書は読めません**。手順書が読めない状況こそが、この手順書を最も必要とする状況です。

そのため、以下のいずれか **2箇所以上** に複製を用意し、**内容を変更したら必ず全箇所を更新**してください。

### 複製の保管先チェックリスト

| # | 保管先 | 用意した日 | 最終更新日 | 備考 |
|---|--------|-----------|-----------|------|
| 1 | **印刷した紙**（事務所の鍵付き引き出し） | | | 電源・ネットワークが全滅しても読める唯一の手段。必須 |
| 2 | **本システムと別のクラウド**（例: 業務用Googleドライブ／OneDriveの別アカウント） | | | 本システムのバックアップ先とは**別のアカウント**にすること |
| 3 | スマートフォンのメモアプリ（画面ロック必須） | | | 外出先で発覚した場合用。任意 |

> ⚠️ **やってはいけない保管先**
> - 本システムが動いているPCのデスクトップ／`C:\workOfficeTani\` 配下だけ
> - 本システムのDBバックアップと同じフォルダ・同じクラウドアカウント
> - このGitHubリポジトリだけ（＝リポジトリの認証情報が漏れた時点で相手にも読まれる）

### この手順書に**書いてはいけない**もの

パスワードや鍵の**実際の値**は、この手順書には一切書きません。書くのは「**どこに何があるか**」だけです。
実際の値は第5章の保管ルールに従って、この手順書とは別の場所に保管します。

## 1. 「インシデント」と判断する基準

以下のいずれかに当てはまったら、迷わず第2章の初動に進んでください。
「気のせいかもしれない」で様子を見るのが一番危険です。**空振りでも構いません。**

| # | 兆候 | 例 |
|---|------|-----|
| 1 | 身に覚えのないログイン | 監査ログに、自分が操作していない時間帯・IPアドレスからのアクセスがある |
| 2 | データが勝手に変わった／消えた | 求職者の件数が減っている。登録した覚えのないレコードがある |
| 3 | パスワードが通らない | 正しいはずのログインパスワード・DBパスワードで入れない（＝変更された疑い） |
| 4 | 身代金の要求 | ファイルが暗号化され、金銭を要求するメッセージが表示された |
| 5 | 外部からの通知 | GitHubから「新しい端末からのログイン」通知。取引先から「そちらの名前で不審なメールが来た」 |
| 6 | 認証情報の流出 | パスワードを書いたメモ・PCを紛失した。トークンを誤って公開の場所に貼った |
| 7 | 動作が明らかにおかしい | 覚えのないプログラムが動いている。PCが極端に遅い。見慣れない通信が発生している |

判断に迷ったら「**インシデントとして扱う**」を選んでください。

## 2. 最初の30分にやること（初動・封じ込め）

順番が重要です。**上から順に実行してください。**

### 手順1: 記録を始める（所要1分）

紙のノート、またはスマートフォンのメモに、**時刻と行った操作**を書き始めます。
後で被害範囲を特定するとき、報告書を書くときに必ず必要になります。
PC上のファイルに書かないでください（そのPCが汚染されている可能性があるため）。

```
記録テンプレート
──────────────────
発覚日時：    年  月  日   時  分
気づいたきっかけ：
最初に見た画面／メッセージ：
（以降、行った操作を時刻とともに記録）
```

### 手順2: ネットワークから切り離す（所要1分）

**PCの電源は切らないでください。** 電源を切るとメモリ上の証拠が消え、
また暗号化の途中だった場合にファイルが壊れることがあります。

- 有線LANの場合：**LANケーブルを物理的に抜く**
- 無線LANの場合：**Wi-Fiをオフにする**（機内モードでも可）

### 手順3: システムを停止する（所要2分）

ネットワークを切ったうえで、本システム（Javaアプリ）を止めます。

```powershell
Get-CimInstance Win32_Process | Where-Object { $_.CommandLine -like '*person-management*.jar*' } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

自動起動が設定されている場合、再起動で勝手に立ち上がってしまうため、
スタートアップフォルダの `start-system.vbs` も一時的に別フォルダへ退避します。

```powershell
Move-Item "$env:APPDATA\Microsoft\Windows\Start Menu\Programs\Startup\start-system.vbs" "$env:USERPROFILE\Desktop\start-system.vbs.disabled"
```

### 手順4: 証拠を保全する（所要5分）

**この時点で、既存のバックアップファイルには絶対に触らないでください**
（上書き・削除・復元のいずれも行わない）。

以下をUSBメモリなど**外部媒体**にコピーします。ネットワークは切ったままです。

| 対象 | 場所 |
|------|------|
| 監査ログ | `C:\workOfficeTani\logs\audit\`（対策2実装後） |
| システムログ | `C:\workOfficeTani\system-log.txt` |
| DBバックアップの一覧（コピーではなく一覧） | `Get-ChildItem C:\workOfficeTani\backup \| Out-File （USB）\backup-list.txt` |
| Windowsイベントログ | `wevtutil epl Security （USB）\security.evtx` |

### 手順5: 認証情報を無効化する（所要10分）

→ **第3章へ進んでください。** ここが最も重要な作業です。

### 手順6: 相談先に連絡する（所要5分）

第8章の連絡先一覧に従って連絡します。手順5より先に連絡しても構いませんが、
**連絡待ちで手順5を止めないでください。**

## 3. 認証情報の即時無効化手順

侵入されている可能性がある以上、**本システムに関わる認証情報はすべて変更対象**です。
「これは大丈夫だろう」で1つ残すと、そこから再侵入されます。

以下の表の**全項目**を、上から順に実施してチェックを付けてください。

| # | 対象 | 無効化の方法 | 完了 |
|---|------|-------------|------|
| 1 | PostgreSQL のロール（`postgres` および `kaseihu_*`） | → 3-1 | ☐ |
| 2 | 本システムのログインパスワード | → 3-2 | ☐ |
| 3 | GitHub のアクセストークン | → 3-3 | ☐ |
| 4 | メール送信用のアプリパスワード | → 3-4 | ☐ |
| 5 | Windows のログインパスワード | → 3-5 | ☐ |
| 6 | バックアップ保存先クラウドのパスワード | → 3-5 | ☐ |

### 3-1. PostgreSQL ロールのパスワードを変更し、全接続を切る

**まず現在つながっているセッションを全部切ります。**（攻撃者が接続を維持している場合、
パスワードだけ変えても既存の接続は生き続けるためです。ここを飛ばすと意味がありません。）

```powershell
$env:PGPASSWORD = "（現在のpostgresパスワード）"
& "C:\Program Files\PostgreSQL\17\bin\psql.exe" -U postgres -h localhost -d postgres -c "SELECT pid, usename, client_addr, state, query_start FROM pg_stat_activity WHERE datname = 'kaseihu';"
```

表示された接続を確認し（記録しておく）、自分以外を切断します。

```powershell
& "C:\Program Files\PostgreSQL\17\bin\psql.exe" -U postgres -h localhost -d postgres -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = 'kaseihu' AND pid <> pg_backend_pid();"
```

続けてパスワードを変更します。**新しいパスワードは、他で使っていない20文字以上のものにしてください。**

```powershell
& "C:\Program Files\PostgreSQL\17\bin\psql.exe" -U postgres -h localhost -d postgres -c "ALTER ROLE postgres WITH PASSWORD '（新しいパスワード）';"
```

> 📌 **対策1（DBロール分離）実装後は、以下のロールも同様に変更してください。**
> `kaseihu_owner` / `kaseihu_app` / `kaseihu_admin` / `kaseihu_ro`
> ```powershell
> & "C:\Program Files\PostgreSQL\17\bin\psql.exe" -U postgres -h localhost -d postgres -c "ALTER ROLE kaseihu_app WITH PASSWORD '（新しいパスワード）';"
> ```
> 変更後は、環境変数 `DB_PASSWORD` の値も合わせて更新しないとシステムが起動しません（→ 第4章）。

**ロールごと止めたい場合**（そのロールでのログインを完全に禁止する）:

```powershell
& "C:\Program Files\PostgreSQL\17\bin\psql.exe" -U postgres -h localhost -d postgres -c "ALTER ROLE kaseihu_app WITH NOLOGIN;"
```

戻すときは `WITH LOGIN` です。

> ⚠️ **ロックアウト注意**：`postgres` ロール自体を `NOLOGIN` にしてはいけません。
> 誰もDBに入れなくなり、復旧手段が失われます。緊急用アカウントについては
> `docs/EMERGENCY_ACCESS.md`（対策1と同時に整備）を参照してください。

### 3-2. 本システムのログインパスワードを変更

環境変数 `LOGIN_PASSWORD` の値を新しいものに変更し、システムを再起動します。
（設定方法は `.env.example` および `SETUP_NEW_PC.md` を参照）

### 3-3. GitHub のアクセストークンを失効させる

1. https://github.com/settings/tokens を開く
2. 本システム用のトークンを探し、**Delete**（または Revoke）をクリック
3. 万一どれか分からない場合は、**全部消して構いません**（後で作り直せます）
4. あわせて https://github.com/settings/security-log で、身に覚えのない操作がないか確認する

トークンを消すと `git pull` / `git push` ができなくなりますが、
封じ込めが最優先です。新しいトークンは落ち着いてから発行してください。

### 3-4. メール送信用のアプリパスワードを失効させる

メール認証（`app.auth.email-enabled: true`）を使っている場合のみ。

1. Googleアカウントの場合：https://myaccount.google.com/apppasswords を開き、該当のアプリパスワードを削除
2. 環境変数 `MAIL_PASSWORD` を新しい値に更新

### 3-5. Windows・クラウドのパスワードを変更

- Windowsのサインインパスワードを変更（`Ctrl + Alt + Del` →「パスワードの変更」）
- バックアップ保存先クラウド（Googleドライブ／OneDrive等）のパスワードを変更し、
  **他の端末からのログインをすべてサインアウト**させる

## 4. 鍵・認証情報の棚卸しとローテーション

### 4-1. 認証情報の一覧（棚卸し表）

「何が、どこにあり、どう変えるか」を1枚にまとめたものです。
**新しい認証情報を追加したら、必ずこの表に行を追加してください。**

| # | 名称 | 用途 | 保管場所（実際の値） | 変更方法 | 推奨ローテーション周期 |
|---|------|------|---------------------|---------|----------------------|
| 1 | PostgreSQL `postgres` パスワード | DB管理者 | 紙（鍵付き引き出し）＋パスワード管理ソフト | 3-1 | 1年 or 人の入替時 |
| 2 | PostgreSQL `kaseihu_app` パスワード | アプリ通常接続 | 環境変数 `DB_PASSWORD` ＋パスワード管理ソフト | 3-1 | 1年 |
| 3 | PostgreSQL `kaseihu_admin` パスワード | 削除操作用 | 環境変数 `DB_ADMIN_PASSWORD` ＋パスワード管理ソフト | 3-1 | 1年 |
| 4 | 本システムのログインパスワード | 画面ログイン | 環境変数 `LOGIN_PASSWORD` | 3-2 | 6ヶ月 |
| 5 | MFAバックアップコード | 認証アプリ紛失時 | 紙（鍵付き引き出し）**のみ**。PC内に保存しない | 再発行 | 使用のつど |
| 6 | GitHub アクセストークン | ソースの取得・更新 | Git Credential Manager（OS の資格情報マネージャー） | 3-3 | 1年（有効期限を設定する） |

| 9 | バックアップ用クラウドのパスワード | 遠隔バックアップ | パスワード管理ソフト | 3-5 | 1年 |

### 4-2. ローテーション時の手順（平常時の定期変更）

**システムを止めずに変更しようとしないでください。** 必ず以下の順で行います。

1. **変更前に必ずバックアップを取る**（`C:\workOfficeTani\backup\backup.ps1` を手動実行）
2. システムを停止する（第2章の手順3と同じコマンド）
3. 新しい値を決め、**先に保管場所（紙・パスワード管理ソフト）へ記録する**
   （システムに設定してから記録しようとすると、記録前に忘れてロックアウトします）
4. DB側／GitHub側の値を変更する
5. 環境変数を新しい値に更新する
6. システムを起動し、**ログインとデータ表示ができることを確認する**
7. 確認できたら、第4章の棚卸し表の「最終変更日」を更新する

### 4-3. 「唯一の命綱」を守る対象と同じ場所に置かないためのチェック

各項目について、**保管場所が2箇所以上あり、かつ片方はシステムの外**であることを確認してください。

| 守るもの | 命綱 | ❌ 危険な置き方 | ✅ 正しい置き方 |
|---------|------|----------------|----------------|
| DB内の個人情報 | DBバックアップ | 同じPCの `C:\` 配下だけ | 同じPC＋別クラウド（別アカウント） |
| DBへのアクセス | postgresパスワード | `application.yml` に直書き | 環境変数＋紙（鍵付き） |
| 画面へのアクセス | MFAバックアップコード | 同じPCのテキストファイル | 紙（鍵付き引き出し）のみ |
| ソースコード | GitHubトークン | `.git\config` のURLに直書き | OS資格情報マネージャー |
| 侵入の証跡 | 監査ログ | アプリと同じDB・同じ権限 | 別ファイル＋追記専用＋別媒体へ日次コピー |
| 復旧の手順 | **この手順書** | このリポジトリ内だけ | 第0章のチェックリストのとおり |

## 5. 復旧手順

**第3章の無効化がすべて完了するまで、復旧作業を始めないでください。**
汚染された状態で復元すると、同じ経路で再度侵入されます。

### 5-1. 侵入経路が特定できていない場合

**PCの初期化（クリーンインストール）から行ってください。**
プログラムだけ入れ直しても、バックドアが残っていれば意味がありません。

`SETUP_NEW_PC.md` の手順に従い、新しい環境を1から構築します。
このとき、**第3章で変更した新しいパスワード**を使ってください。

### 5-2. データの復元

侵害された日時が特定できている場合、**その日時より前の**バックアップを選びます。

1. まず**試験復元**で中身を確認します（本番DBに触れません）

```powershell
$env:PGPASSWORD = "（新しいpostgresパスワード）"
& "C:\Program Files\PostgreSQL\17\bin\createdb.exe" -U postgres -h localhost kaseihu_test
& "C:\Program Files\PostgreSQL\17\bin\pg_restore.exe" -U postgres -h localhost -d kaseihu_test "C:\workOfficeTani\backup\（ファイル名）"
& "C:\Program Files\PostgreSQL\17\bin\psql.exe" -U postgres -h localhost -d kaseihu_test -c "SELECT count(*) FROM persons;"
```

2. 件数・内容が妥当であれば、本番DBへ復元します（詳細は画面「1-7-5 バックアップ手順」の③を参照）

### 5-3. 復旧後の確認リスト

- ☐ ログインできる
- ☐ 求職者・求人者の件数が復元前の想定と一致する
- ☐ 監査ログが再び記録され始めている
- ☐ 自動バックアップのタスクが有効（`Get-ScheduledTask -TaskName "kaseihu-DB-Backup"`）
- ☐ スタートアップの `start-system.vbs` を元に戻した
- ☐ 第4章の棚卸し表を、新しい値の情報に更新した

## 6. 被害範囲の特定

報告義務の判断（第7章）に必要です。以下を確認し、**紙に記録**します。

| 確認項目 | 確認方法 |
|---------|---------|
| いつから侵入されていたか | 監査ログの、最初の不審なアクセスの日時 |
| どの画面が閲覧されたか | 監査ログの画面URL一覧 |
| 何件の個人情報が対象か | 閲覧された画面から推定（例：求職者一覧を開かれた＝在職中の求職者全件） |
| データが持ち出されたか | 通信ログ・大量のPDF/Excel出力の記録 |
| データが改ざん・削除されたか | 直近バックアップとの件数比較 |

> 監査ログがない期間については「**特定できない＝全件が対象の可能性がある**」として扱ってください。
> これが対策2（監査ログ）を優先して実装する理由です。

## 7. 外部への報告

> ⚠️ 以下は一般的な情報です。実際の対応は弁護士・所轄官庁にご確認ください。

個人データの漏えい等が発生し、**個人の権利利益を害するおそれがある**場合、
個人情報保護法により**個人情報保護委員会への報告**と**本人への通知**が義務付けられています。

| 報告先 | 期限の目安 | 窓口 |
|--------|-----------|------|
| 個人情報保護委員会 | 速報：**3〜5日以内** / 確報：30日以内 | https://www.ppc.go.jp/ |
| 本人（求職者・求人者） | 速やかに | 電話・書面 |
| 警察（サイバー犯罪相談窓口） | 速やかに | 各都道府県警 |
| IPA 情報セキュリティ安心相談窓口 | 随時 | https://www.ipa.go.jp/security/anshin/ |
| 労働局（有料職業紹介事業の許可元） | 要確認 | 事業所管の労働局 |

**報告時に必要になる情報**は第6章で記録したものです。
記録がないと報告書が書けないため、第2章の手順1（記録開始）を飛ばさないでください。
